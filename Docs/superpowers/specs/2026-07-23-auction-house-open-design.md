# 拍卖行开放通知修复设计

## 目标

修复角色登录后打开拍卖行时显示“已暂时关闭拍卖行”的问题，让客户端进入拍卖行界面。

## 已确认现象与证据

- 登录流程会发送两条 `0x00B7` 服务状态通知。
- 当前两条通知的正文分别是 `00 00` 和 `01 00`。
- 拍卖专用协议构建器将正文固定编码为两个字节：`[serviceType, state]`。
- 用户观察到当前客户端将这一登录状态显示为拍卖行暂时关闭。

因此，本次修复把 `state=0` 作为关闭状态、`state=1` 作为开放状态处理。客户端处理函数尚未被静态分析直接定位，所以该语义属于由现有线协议与客户端表现共同支持的最小假设。

## 范围

本次只开放拍卖行入口：

- 登录时为现有两个服务类型发送开放状态。
- 保持现有通知顺序、命令号和封包结构不变。
- 添加精确线字节自测，锁定开放通知。

本次不实现拍卖列表、搜索、上架、购买、结算、持久化和 GM 管理功能，也不修改客户端二进制、PVF 或数据库。
因此本切片只建立 `Auction Protocol` 的最小构建边界，不提前创建空的 Auction Core、Storage、Mail、Asset Adapter 或 AuctionHandler。

## 设计

### 状态与服务类型

在服务通知构建代码中使用具名的内部枚举或常量，避免登录处理器继续散布裸字节：

- 服务类型 0：`0x00`
- 服务类型 1：`0x01`
- 关闭状态：`0x00`
- 开放状态：`0x01`

由于两个服务类型的业务名称尚无可靠证据，代码命名只表达编号，不推测其具体业务含义。

### 单一构建入口

由 `Network/Builders/Auction/AuctionServiceNotificationBuilder` 提供“构建拍卖行开放通知”的单一入口，返回两条完整的登录通知：

1. `cmd=0x00`、`type=0x00B7`、正文 `00 01`
2. `cmd=0x00`、`type=0x00B7`、正文 `01 01`

`LoginHandler` 只遍历并发送该入口返回的通知。这样自测验证的就是登录路径实际调用的构建逻辑，而不是一套测试专用字节。
通知类型使用 `NotiPacketType.AUCTION_NOTIFY_AUCTION_SERVICE`，避免与同号的入站命令混淆。

### 兼容性与失败行为

- 不改变通知数量、顺序、命令号或正文长度。
- 构建过程无数据库、配置或网络依赖，不增加新的运行时失败分支。
- 若客户端仍拒绝进入拍卖行，停止扩展业务实现，转为显式客户端抓包或处理函数逆向，重新确认 `state` 语义。

## 测试驱动实现

1. 先添加并注册聚焦自测，断言两条完整通知的命令号、类型、长度及正文分别为 `00 01`、`01 01`；在生产实现前确认测试失败。
2. 添加具名状态与服务类型，并实现统一的开放通知构建入口。
3. 修改 `LoginHandler` 使用该入口。
4. 运行聚焦自测、Debug 构建和全量自测。

全量自测的既有基线是 59 套中 58 套通过，唯一失败为与本任务无关的 `character-option` 迁移版本断言。本修复不得新增失败。

## 验收标准

- Debug 构建通过且无新增警告或错误。
- 聚焦自测通过，并证明登录路径使用的两条通知正文为 `00 01` 和 `01 01`。
- 全量自测不产生新的失败。
- 按项目规则，本轮不启动服务器或客户端；“客户端实际可打开界面”保留为后续显式 UI 验证项。

## 回滚

回滚统一构建入口及 `LoginHandler` 调用即可恢复原有两条关闭状态通知，不涉及数据迁移或持久化回滚。
